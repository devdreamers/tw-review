# 정보 구조 원칙

문서를 읽는 사람 입장에서 정보를 설계하는 게 핵심이에요. 아래 여섯 가지 원칙을 기준으로 문서 구조를 리뷰하세요.

## 1. 한 페이지에서는 하나만 다루기

### 체크리스트

- 제목 깊이가 `#### (H4)` 이상이면 문서를 나누는 것을 고려했는가?
- 개요를 다루는 페이지를 활용해서 여러 개념을 개략적으로 소개하고, 각 항목은 별도 문서로 연결했는가?
- 한 페이지에서 두 개 이상의 핵심 주제를 다루고 있지 않은가?

## 2. 가치를 먼저 제공하기

기능 중심의 설명보다는 독자가 얻을 수 있는 가치를 먼저 설명하세요.

### 체크리스트

- 부가적인 정보나 세부 사항을 나중에 배치했는가?
- 기능 나열보다 "이 기능이 왜 유용한지"를 먼저 전달했는가?

### 예시

```diff
- 리버스 프록시 설정은 2019년에 도입되었고, 많은 수정이 있었습니다...
+ 리버스 프록시 설정을 적용하면 네트워크 지연 문제를 최소화할 수 있어요.
```

## 3. 효과적인 제목 쓰기

### 체크리스트

- 제목에 핵심 키워드가 포함되어 있는가? (예: "에러를 해결하는 방법은?" → "`NOT_FOUND_USER` 에러를 해결하는 방법")
- 같은 수준의 소제목이 일관된 문체(동사형 또는 명사형)를 따르는가?
- 제목이 30자 이내로 간결한가?
- 제목이 평서문인가? (느낌표/물음표 지양)

## 4. 개요 빠트리지 않기

### 체크리스트

- 개요가 제목 바로 아래, 본문 시작 전에 배치되어 있는가?
- "이 문서를 읽으면 무엇을 할 수 있는가?"에 대한 답을 개요에서 제공하는가?
- 기술적 배경 설명보다 핵심 정보(독자가 얻을 가치)를 먼저 제공하는가?

## 5. 예측 가능하게 하기

### 체크리스트

- 일관된 제목, 형식, 구조를 유지했는가?
- 섹션 제목이 문서 전체에서 동일한 패턴을 따르는가? (예: "설치"와 "환경 설정"을 혼용하지 않았는가)
- 기본 개념 → 구체적 사용법 → 예제 코드 → 심화 내용의 논리적 순서로 배치했는가?
- 용어를 일관되게 사용했는가? (하나의 문서 안에서 "상태"와 "데이터", "값"을 같은 의미로 혼용하지 않았는가)

## 6. 자세히 설명하기

### 체크리스트

- 새로운 개념이 처음 등장하면 한두 문장으로 정의를 설명했는가?
- 기능이 어떤 조건에서 어떻게 동작하는지 충분한 정보(단위, 조건, 예외 상황)를 제공했는가?

### 예시

```diff
- 이 서비스는 이벤트 소싱 방식을 사용해 상태를 관리합니다.
+ 이 서비스는 이벤트 소싱(Event Sourcing) 방식을 사용해 상태를 관리합니다. 이벤트 소싱은 상태의 최종 결과만 저장하는 대신, 상태 변화를 일으킨 모든 이벤트를 기록하는 방식입니다.
```
